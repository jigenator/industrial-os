# Architecture

Status: current at Pi Reloader contract version 2, with the sidebar redesign of 2026-11-18, its split into parts with a storybook, and the droid-plate pane header and the Pi Reloader folded into the one `industrial-os` mod ([decision](../../docs/decisions/herdr-combined-mod.md)).
Evidence: the mods and layout, their tests, the redesign's [probe-window record](../CONTRIBUTING.md#sidebar-redesign), and Herdr app 0.1.15's own documentation in `~/.config/herdr-app` (`AGENTS.md` "Layouts", "Keys", "Commands" and "Mods", `herdr.d.ts`, `gpui-kit.d.ts`, whose `net` module offers only `connect(host, port)`), `herdr-app commands`, herdr-core 0.1.20's `hc --help` and `hc --skill`, its shipped `main` layout and `agents`, `spaces`, `confirm` and `picker` mods.

No code is shared with another project at run time, except the mod's `ds/` copy of design-system files, which the pane header draws with (see [droid-plate](#droid-plate)); the sidebar's vocabulary is a committed copy of values. ## Flow

herdr-app redraws each of the mod's three blocks whenever its live data changes: spaces, agents, panes, terminals (including their labels), focus and theme. Each block is its own copy of the view. Each render reads those lists once and passes them with the clock, this computer's home folder, the last ahead/behind results, the remembered state, the folded spaces, the focused pane and the shown view to `buildSidebar`. Only the list block saves the new memory, sets the agent order and looks up `git`; the top block reads the same data for its counts and map and keeps nothing. `buildSidebar`:

1. Parses the label on every live terminal whose agent status `app` is `pi` (from `agents()`, else the core's report). Anything else is no signals.
2. Builds one Pi block per agent with signals and one line per other agent, in `agents()` order, updating each terminal's remembered counts and finished time.
3. Builds one row per space from its panes, using the Pi blocks' states (SUB/RUN as working) and units, and updates its remembered activity.
4. Builds the missions from every pane, with the blocks' states and readings, then ACTION REQUIRED, the agents view, the rail's lamps and the counts.
5. Returns the earliest time any shown clock, age or quiet age will change.

**Drawings.** A render asks for each drawing by a key (`picture(key, make, …)`). The first time, the key is queued and its place stays empty; the block's clock writes queued drawings to `.gen/` as SVG files named by their content, and the next render places them. Each block has its own queue. **The map** is a `MapView` per open space, and one in the plate, created and released by the block's clock, never during a render. Each has a 33 ms clock of its own and reads its block's shared `stage` (the world, the hovered unit, the watched unit), so the map moves without redrawing the list. **Two more nested views** read the same stage, both made once when the list block starts: `GroundView` draws [the ground's light](design.md#ground) on the same 33 ms clock from the pointer's place, which the list's `on_mouse_move` only records; `ReadoutView` draws the scanner's readout and is redrawn by a 30 ms timer that the list starts when the pointer reaches a pane and cancels 1.2 s later. **Between blocks** there are two channels, both `shared()` keys. `industrial-os.aim`: the list sets it to the ACTION REQUIRED unit under the pointer and the plate's crosshair follows. `industrial-os.motion`: `{ at, kind, step }` of a [fold in motion](design.md#folding-and-unfolding); the block that was asked sets each step from timers and every block draws its own covers for it. **Herdr's own mods** are opened by name, never imported: `picker` from the search hint, `menu` (as a popup, with a tab as its target) from a right click on a tab title. One older than 3 s is ignored, so a mod reloaded mid-fold leaves nothing behind. **The scanner** is one element per list. In the scrolling list its place is measured, not computed: a pane's `on_mouse_move` bounds against the list body's, taken from the same pointer move.

One 110 ms clock per block writes drawings, steps the state marks while a moving one is shown (and the open grip's chevrons), and every ninth tick compares the clock with that time and redraws only then; it also starts ahead/behind lookups: a place (machine and folder) not looked at yet at once, others every 30 seconds while the window is active, one pass at a time with a 5-second timeout per `git` run. A failed run keeps what was shown.

## Droid-plate

The layout's pane frame names `industrial-os` with `props: { "part": "plate" }` as its header, so the app keeps one copy of the mod per pane of the shown tab with `props().pane` and `props().terminal` (`~/.config/herdr-app/AGENTS.md`, "Pane frames"). Each copy:

1. **Reads** in render: its `PaneInfo` from `panes()` (app, program, status, focused, zoomed, folder, branch, title), its terminal from `terminals()` (argv, columns, labels), the `io.signals.v1` label when the app is `pi` and the terminal is live, and `window().active`, which `herdr.d.ts` documents as live. A 500 ms timer redraws when the window's answer changed since the last draw, in case activation does not redraw a pane header; it does nothing otherwise, and stops in a copy that is not shown (two asked-for redraws that never came) until it renders again.
2. **Remembers** per copy: when Pi was first seen (STARTING's 3 s), when it handed back (PI EXITED until the next command), when the foreground program and an agent's work started, the motion timeline, and composed headers (at most 48, keyed by their inputs).
3. **Looks up** the foreground command with `hc get <terminal> --json` (herdr's `hc`), once per change of program or title, one at a time, bounded at 2 s; its `foreground.argv` is the RUNNING text and its `cols` the width until `terminals()` reports one. A failure keeps the program's name.
4. **Composes in a task.** herdr-app's QuickJS runtime interrupts a render after about 50 ms (measured with `herdr-app check`: 50 ms passed, 60 ms failed; tasks and `init` ran to about 500 ms), and a 99-column plate takes about 15–30 ms there. So render only reads and compares what it should show with what it last asked for; on a change it starts one task that composes the needed headers (`plate.js`), advances the timeline (`motion.js`) and turns each lighting layer's frame into pieces (cached per composed header). Render draws the pieces that task left, so a change shows one task turn late. A lighting change (T2, H1) is a new layer drawn in four bank boxes at opacity 0 and, 20 ms later, at 1 with each bank's delayed `.transition("opacity")`; the reveal draws the outgoing plate's rows as right-anchored clips whose `.transition("width")` takes them to 0. Herdr animates both natively. Only the character-level motions (CRT boot, K5, latch, K4) compose frames on a timer, at 40 or 50 ms, and only while one plays (about 25 ms a frame at 198 columns in `herdr-app check`); one wake (`clock.js`) brings the copy back for the next clock second, STARTING's end, the next K4 ghost, priming and settling. A timer that has asked twice for a redraw that never came (the copy is not shown) stops, and the next render restarts what is due.
5. **Measures the grid.** The header's width comes from its own layout (`on_size_change`), and the terminal font's advance from a transparent 16-character probe in that font at the terminal's size. Herdr places terminal cells as Ghostty does, the advance times `terminal_cell_width` rounded up to a whole device pixel, and a mod is not told the display's scale, so `cellWidthOf` takes the scale (2, 1, 3, 4) whose cell gives Herdr's column count across the header: measured live at 2x, JetBrains Mono 14's 8.406 px advance is the 8.5 px cell, 198 columns in 1684 px. The plate is then `floor(width ÷ cell)` columns, and the part of a cell left over at the right takes each row's last color. Until both are laid out it uses the terminal's columns and `font_size × 0.6`. At most 256 of those columns are composed (`DRAW_LIMIT`); a wider header's plan widens the drawn rows from 19 cells before their right edge, repeating the plain ground there, and the motions run on the drawn rows, so a wide pane costs what a 256-column one does. One render draws at most 2,400 pieces (`PIECE_BUDGET`), shared by the lighting layers and the reveal on screen: a plan over its share joins its ground and hairline runs across colors at most 2, 4, 8 or 16 apart per channel (`coarsen`), inks, the peak, the strip and the bay untouched. A single plate never needs it; during a switch the layers do (measured in `herdr-app check`: a two-layer switch at 256 columns composes in about 250 ms and draws in 8–15 ms, a 198-column one drew in 32–34 ms before the budget was shared).
6. **Draws** every piece absolutely, at x = col × cell (snapped to the device pixel) and the row's top (rows of 18.5 px and a 19 px strip), never as flowing text, whose glyph advance (8.406 px) is not the cell (8.5 px): background rectangles, adjacent cells of one color merged; the glyphs a terminal draws as shapes, from the design system's `GLYPH_SHAPES` (block elements, so the barcode's bars and the wordmark's pixels fill their cells and join across rows; light lines; the peak's Powerline triangles, as one-device-pixel bands, since herdr-app's `svg` keeps its aspect ratio and cannot stretch a triangle to a cell); and one text element per text cell, a cell wide and centred, in the terminal's font (`font_family`, Herdr's JetBrains Mono by default). Nothing depends on a font the app may lack: text is ASCII, `®`, `■ ● ○ ▶ ▲` and `…`, which JetBrains Mono has, and `⟁` is `mark.svg`. The bay's keys are their own elements with the key's hit cells, hover and press, running `pane.split {direction}`, `pane.zoom` and `pane.close` with the pane, as the shipped `pane` header does; a click elsewhere runs `pane.focus`.
7. **Labels its terminal** `io.droid-plate.v1=1` when it first draws for that terminal and moves the label when the terminal changes, through `labels.js`: what the copy wants is kept apart from what `hc` acknowledged, one worker sends the writes one at a time (each bounded at 2 s, a terminal's next write waiting for its earlier one), so a set and a clear never land out of order; a terminal no longer wanted is cleared before the new one is set; a failed write is retried after 250, 500 and 1000 ms, then left until what is wanted changes. `close()`, which the app calls when the pane, tab or layout-owned slot goes and on quit (at most 250 ms), supersedes every pending write and clears every terminal that may carry the label, after a write in flight has landed (at most 100 ms). The [droid header](../../pi/droid-header/docs/architecture.md#flow) reads it once at Pi's session start to show its ledger alone. Not called for a hidden copy or an inactive tab, whose plate still exists, so its label stays.

Colors in the drawn rows are design-system values carried by the composed lines (resolved to hex by `ds/foundation/cells.mjs`), not `theme()` names: the plate is the design system's, as it is in the terminal.

`ds/` holds exactly the design-system modules the pure modules import and everything they import (21 files), byte for byte; `node herdr/scripts/sync-design-system.mjs` rewrites it and `test/droid-plate.test.mjs` fails while it differs. The design system's text functions use `Intl.Segmenter` when the host has it and code points otherwise: the mod runtime has no `Intl`.

## Pi Reloader

`mod.open:industrial-os` opens the mod's `mod.json` overlay as a window, with `part: "reloader"` in its props, so the root view is the Pi Reloader; it needs no layout. Its commands carry the piece's name (`industrial-os.reloader-reload`, `-reset`, `-close`), because every copy of the mod on screen hears every command. As a window, a press it doesn't stop doesn't close it, and Esc reaches the mod, which ignores keys while a run is going. A run is one `cx.spawn` task; `reloader.js` gets an `io` whose every call goes through herdr-core or the guard, so the whole sequence is tested with a simulated one.

```mermaid
flowchart LR
    Agents["agents(), terminals(), layout()"] --> Select["selectCandidates"]
    Select --> Seq["runAll: reloadOne / resetOne"]
    Seq -->|"hc get --json"| Core["herdr-core"]
    Seq -->|"JSON line, net.connect 127.0.0.1:port"| Guard["pi/reloader-guard in each Pi"]
    Guard -->|"ctx.reload() / ctx.shutdown()"| Pi["Pi"]
    Seq -->|"hc send t 'pi --session …' (reset, shell in front)"| Core
```

1. **Select.** From `agents()`: Pi (`app` is `pi`) on this computer, in a pane, not shown by a layout block nor named `lunalee-chat`, idle or done. Other Pi agents are counted as busy or protected; other agents are ignored. A window's `only` prop narrows the set.
2. **Run.** Both actions start on every candidate at once and wait for every attempt; each ends completed, skipped with a reason, or failed with a reason.
3. **Check at action time.** `hc get <t> --json` must show it live, Pi's status idle or done, and a valid `io.pi-reloader.v2` label; else skip, or fail without a guard, with nothing done.
4. **Reload:** probe; if ready, `reload` with the probed session; then poll `hc get` until the label shows a new token and a probe on it answers (30 s).
5. **Reset:** the root program must be sh, bash, zsh, dash or ksh with Pi as a job; probe; a session file is required; `quit`; poll until the shell is in front with no agent status (15 s); `hc send` the single-quoted resume line; poll until Pi reports idle or done with a new label and a probe returns the same session (30 s).

Neither action moves focus or marks anything read. Neither advances herdr-core's per-terminal `turn`, so Herdr's idle or done for each Pi stays as it was; see [the decision](../../docs/decisions/pi-reloader-desktop.md). The polls run only while the mod acts: `hc wait` waits for an agent to stop working, and these Pis are already settled.

Commands from `nextCommand()` (`reloader-reload`, `reloader-reset`, `reloader-close`) reach the window only while it is open; it ignores every other command of the mod.

## Where the next change belongs

- A rule about what a value means: the pure module that owns it, with its test, then [the design](design.md#sidebar).
- A color, opacity, status word, designation or state mark: the design system's `sidebar-vocabulary.mjs` first, then `node scripts/sync-vocabulary.mjs`.
- Something the map shows: `map.js`. A halo, grid or fade: `assets.js`. Both return SVG documents; neither places anything.
- How one piece of the sidebar is drawn: its file in `parts/`, with its contract comment and its story in `stories.js` ([parts](parts.md#adding-or-changing-a-part)). A piece drawn in two places becomes a part before it is drawn a second time.
- Where the parts sit, what the pointer does, which command a click runs: `main.js`.
- What a pane plate shows or when it moves: `mods/industrial-os/plate/model.js` or `motion.js` and their test, then [the design](design.md#pane-plate); how it looks: the design system first, then `ds/` regenerated.
- Another piece of Industrial OS in the app (a header, a window, a block): a folder inside `mods/industrial-os/` with a `view.js` and its pure modules, a `part` in `main.js`'s `WHOLE`, and the folder's name in the layout test's `FOLDERS`; not a mod of its own, which could share no file with this one ([decision](../../docs/decisions/herdr-combined-mod.md)). The mod has one `mod.json` window, the Pi Reloader's; any other window is opened by the mod with `openOverlay`, as the storybook is. A layout is a file under `layouts/`, with a test beside the others and an install section in the README. A keys.json snippet goes in `keys/`.
- A Pi Reloader rule: `reloader.js` and its test; a protocol change starts in the [guard contract](../../pi/reloader-guard/docs/contract.md).

## Limits and evolution

- `herdr-app check` loads a mod with empty in-memory state and renders once, as the list block (its props name no part), so the pane header and the Pi Reloader are loaded but not drawn; it does not lay out, run timers, later async states or real data. The stand-in builds populated trees and runs timers and handlers in Node, but paints nothing; a populated look needs the storybook or the sidebar in an [isolated app](../CONTRIBUTING.md#isolated-app), or the live app.
- The storybook's states are set by its stories, not by the pointer: a state "under the pointer" is drawn as if it were. Only the ground's light and each part's own `hover` styles follow the real pointer there.
- herdr-app lets a mod list folders only inside the user's home folder. With an app home outside it (an isolated app in `/tmp`), the mod cannot list `.gen/`, so it rewrites the drawings it needs at each start and never empties the folder.
- The three blocks are separate copies of the view. Whether they share module state is herdr-app's choice, so nothing relies on it: each keeps its own drawings queue and stage, and they talk only through `shared()`.
- Drawings are files: a new text's halo appears a tick after the text. Names are content hashes (FNV-1a and length), so a changed drawing is a new file and the folder only grows; past 1500 files the mod empties it at its next start and rewrites what it needs.
- The map and the marks cost CPU: roughly 16 points of one core for three open spaces and the plate at 30 frames a second (6 to 9 at 20), measured roughly in a probe window ([record](../CONTRIBUTING.md#sidebar-redesign)). They do not stop while another app is in front, by the operator's choice, and the ground's light adds a redraw of its own at the same rate that was not measured. 30 frames a second is the operator's choice over the 20 first shipped.
- Remembered state is per mod copy and per screen. A second copy of the mod (another layout) keeps its own.
- The layout copies Herdr app 0.1.15's `main`; a later `main` is not followed. The layout test records the copy it was made from.
- Lunalee's column names its terminal, so the block is resolved when the layout is built: a terminal started later attaches only after the block is hidden and shown again. When that terminal ends, Herdr deletes the block from the installed copy; re-copying the file restores it. `layout.set` would wipe the layout's `.state` clicks, so nothing here or in Lunalee uses it. Observed live by Lunalee's slice-0 check with herdr-app 0.1.15, not by this project.
- The Pi Reloader's run lives in its window's task: a layout switch closes the window and stops it. So does saving any file of the installed mod, which reloads every copy of it: the sidebar and every pane header start again (a pane's remembered times with them), and a run in progress ends where it was. An install is done with no run going.
- Herdr gives a mod one view class, so `main.js` makes the pane header's or the Pi Reloader's view itself and hands it `init`, `render` and `close`. Seen to work in an isolated app on herdr-app 0.1.16 (timers, tasks, focus and the commands reach the inner view through the root's `cx`); nothing in Herdr's documents promises it.
- The desktop theme is a herdr-app theme file. Its check proves its values, not that the app accepts it: herdr-app validates on load and writes `settings.error` or a layout's `.error` when it rejects one, so a live install is checked with `herdr-app status`.
- The pane header infers the display scale from the advance and Herdr's columns; when no scale matches (an unusual cell-width multiplier or font), the cell is the header's width over the columns, still exact at both edges but up to a fraction of a pixel per column off the terminal's cells. The peak's edges step one device pixel at a time, without antialiasing. The label's clearing on a layout switch was seen in an isolated app, for the shown pane. Its activation fallback and the native T2, H1 and reveal on a real focus or hand-back are unverified live (a probe proved Herdr's delayed per-bank opacity and width transitions; the plate's own were not watched, since the live app could not be focused for it). Over 256 columns the plate's middle is plain widened ground.
